# Agent playbook

Краткий регламент работы агентов по этому репозиторию. Канон: `Ai.Context/`.

## Роли

| Роль | Задача |
|---|---|
| **Human** | Цель, ограничения, DoD; один таск → один агент |
| **Coordinator** | Разбивка, маршрутизация, сверка статуса; не трогает Editor без нужды |
| **unity-pc worker** | Локальный Editor/терминал/файлы на Windows-ПК |
| **Ai.Context** | Долгоживущий канон (этот раздел, `project-context`, preferences) |
| **Ai.Issues** | Архив: `bugs/` и `features/` — проблема → причина → что сделали |

## Kickoff template

Перед стартом зафиксировать:

- **Goal** — что сделать (одна задача)
- **Constraints** — что нельзя / лимиты
- **Paths** — релевантные файлы/сцены/скрипты
- **DoD** — как понять, что готово
- **Don't-touch** — что не менять

## Context gathering (минимум ops)

1. Прочитать `Ai.Context/README` + этот playbook + `project-context`
2. `Ai.Issues` — только связанные с задачей записи
3. Console errors — только по этой задаче
4. Только нужные GameObjects/скрипты — без полного скана `Assets/`
5. Play Mode — только если DoD требует
6. Не искать Agent Store по диску
7. Один фикс → одна проверка → стоп

## Советы человеку

- Одна задача — один агент
- Геймплей и доки — отдельными коммитами, когда удобно
- Worker `unity-pc` держать онлайн, если нужен Editor

## Сессии и Unity-worker

1. **Подсессии.** Не создавать новые сессии (`start_session`) без подтверждения пользователя: сначала описать, зачем и что она сделает, и ждать ответа. `SendMessage` в уже существующую сессию подсессией не считается.
2. **Учёт сессий.** В конце задачи и по вопросу пользователя перечислить созданные или задействованные сессии: название, id, статус, задача.
3. **Один автор на файл.** WIP Enemy/Aggro другого агента не трогать (`Aggro.cs`, `Follow.cs`, `AgentMoveToPlayer.cs`, `AnimateAlongAgent.cs`, `RotateToHero.cs`, `TriggerObserver.cs`, `CheckAttackRange.cs`). Перед правкой любого файла перечитать его с диска: пользователь мог его изменить.
4. **Unity-worker.** Команды Unity CLI — через свою связанную сессию-исполнитель (сейчас `unity-reader`, `local_d6a7af1a-2068-4e0f-8011-33108e0fc865`, Haiku) и `SendMessage`; по умолчанию только чтение. Worker чужой сессии не использовать: его отчёты уходят родителю. Запуск пунктов меню и изменения пакетов — только с подтверждения пользователя.
   - Отчёт своего (связанного) worker'а приходит координатору сам по окончании хода. Не опрашивать в цикле и не выдавать результат, которого нет. Refresh/перекомпиляцию worker без явного разрешения пользователя не делает — проще попросить пользователя переключиться в окно Unity.
5. **Префабы, сцены, контроллеры.** Агент не правит YAML `.prefab`, `.unity`, `.controller` напрямую (ссылки `fileID`/`guid` и overrides ломаются молча). Разовые настройки делает пользователь в Inspector/Animator по точным шагам от агента; повторяемые — Editor-скриптом (`Tools → …`, см. `Knowledge/conventions/unity-editor-tools.md`), запускает пользователь. JSON-ассеты без ссылок (`.inputactions`) править можно. `Assets/Resources/Yurowm/*` — только по прямой задаче.
6. **Проверка.** «Сборка прошла» — только по выводу консоли: `0 error CS` или полный текст ошибок. Догадки не считаются.
7. **Git.** Не коммитить и не пушить без явной просьбы пользователя. Git-статус сообщать отдельно.
8. **Бриф.** Задача вне `Ai.Tasks`-брифа — остановиться и спросить. Бриф отстал от кода (пункт уже сделан, файл переехал) — сообщить и предложить обновить бриф, работу продолжать.

## Ревью (проверяющая сессия)

Общие правила ревью — в `D:\Unity\Knowledge\process\self-review.md`. Проект-специфично здесь:

- Проверять namespace и путь файла (`Game.Scripts.*` и папка совпадают).
- Проверять, что `Ai.Tasks`-бриф (если есть) совпадает с diff.
- Не принимать «сборка прошла» без `error CS` в логе или без результата `unity`.
- Не ревьюить WIP Enemy/Aggro чужого агента без просьбы координатора.
- Замечания — максимум 5 пунктов суммарно (Observations/Risks/Proposals).

## После успеха

Добавить или обновить запись в `Ai.Issues/bugs/` или `Ai.Issues/features/` (`YYYY-MM-DD-short-kebab.md`).

## После задачи: отчёт

После **каждой** задачи в ответе человеку:

1. **Что сделано** и **какие файлы изменены**.
2. **Привязки ввода**, если добавлены, — особенно не-мышиные (геймпад, экранные кнопки).
3. **Что проверено и что нет** (по правилу «Проверка» выше).
4. **Сессии**, если были задействованы (см. «Учёт сессий»).
5. Короткие секции Observations / Risks / Proposals (суммарно **не больше 5 bullets** по всем трём):

- **Observations** — странности в коде / сцене / процессе агента
- **Risks** — что может сломаться
- **Proposals** — улучшения архитектуры / `Ai.*` / workflow агента

**Только предложения.** Нельзя реализовывать рефакторинги из этой секции, пока пользователь явно не скажет. Согласовано с `course-reference`: drive-by improvements запрещены; **предлагать** — можно и нужно.

На что смотреть:

- path ≠ namespace
- misuse папок `Interfaces/`
- drift от CodeBase курса
- устаревший `Ai.Context`
- лишние full-repo scans / ненужный Play Mode
